## Findings

### C01 — Medium: tied scores have different ranking semantics across evaluation, fusion and overlap

`05_retrieval_evaluation/01_metrics.py:27-40` validates hits but preserves the incoming order in `all_rankings`; installed `sentence_transformers/sentence_transformer/evaluation/information_retrieval.py:497-512` instead re-sorts every list by descending score then ascending corpus ID. BM25 deliberately breaks equal scores by corpus position (`16_hybrid_retrieval/01_bm25.py:21-23`); its stored ordering is converted to unique rank scores for RRF (`16_hybrid_retrieval/02_fusion.py:12-15`), and TrecTools consumes stored row order (`20_comparison/02_agreement.py:15-23`; installed `trectools/trec_run.py:164-185`). Consequently tied documents can have one order for effectiveness and another for fusion/inspection. Ties at the cutoff also use selection by corpus position before the evaluator can impose its ID tie-break. BM25 has real score ties by construction, notably zero-score matches, though whether they affect this sampled run requires data execution.

Minimal correction: choose one explicit total order, preferably `(-score, corpus_id)`, for selecting and storing hits in all rankers, including boundary ties, and use that same normalized ranking in `evaluate_run`, fusion and displays. If instead preserving a deliberate input order, assign rank-derived scores for the evaluator as well and document that choice. Do not change only the display.

### C02 — Medium: cross-row known positives can become in-batch negatives

`11_bge_finetuning/01_data.py:15-22` retains all known positives per training query but passes only one selected positive text per row into MNRL. `12_negative_mining/01_mine.py:25-35` excludes known positives only for each row's own explicitly selected negative. Installed `sentence_transformers/multi_vector_encoder/losses/multiple_negatives_ranking.py:21-28,136-186` confirms that other rows' positives and explicit negatives enter each query's denominator; the dense loss has the same in-batch-negative objective. `NO_DUPLICATES` (`11_bge_finetuning/02_train.py:29-37`, `12_negative_mining/02_train_compare.py:24-32`, `13_colbert_finetuning/01_train.py:21-30`) prevents duplicate texts, not a different document known positive for another query. Thus the implementation does not enforce the protocol's exclusion of *every known positive* in the actual loss, even though the explicit-mining assertion passes. Whether a collision occurs in this selected sample/batch schedule has not been established statically; unjudged false negatives remain even after known-label filtering.

Minimal correction: before training, construct/verify batches so no other row's positive or explicit negative is in any query's known-positive set, or use a native loss that can mask multi-positive candidates; retain the partial-judgment caveat. If such a fix is deliberately out of scope, change the contract/claims and report a measured collision audit instead of implying complete exclusion. Do not use test labels to filter training.

### C03 — Medium: rewrite request permits a tool call but assumes text

`17_retrieval_tools/02_rewrite.py:9-13` supplies `tools=[search_tool]` to a request asking for a textual rewrite, then immediately calls `.strip()` on `message["content"]`. A valid OpenAI-compatible assistant tool-call message may have `content: null`; this is already a supported branch in the immediately preceding tool example (`17_retrieval_tools/01_tool_call.py:17-32`). If the model invokes the tool instead of returning a rewrite, the notebook raises `AttributeError` before its intended empty-rewrite check. This is a concrete valid response shape, not a claim about the model's actual response.

Minimal correction: omit `tools` for this text-only rewrite request and explicitly validate that returned content is a nonempty string before stripping. The earlier allowlisted tool round remains unchanged.

### C04 — Medium: training and inference can retain the complete multi-vector index on CUDA

`09_late_interaction/02_encode.py:9-10`, `09_late_interaction/05_reason.py:14-17` and `13_colbert_finetuning/02_evaluate.py:11-13,22-23` encode the complete corpus with default `convert_to_numpy=False`. Installed `sentence_transformers/multi_vector_encoder/model.py:750-760,912-935` says these variable-length tensors remain on the model device. Chunking in `09_late_interaction/04_rank.py:10-18` limits the *scoring call*, not resident corpus storage. The trained-model code calls full all-pairs similarity, but importantly the installed scorer itself chunks token intermediates by default (`util/similarity.py:379-419,449-466`); it is inaccurate to claim that call necessarily materializes the full token similarity tensor. Nevertheless the complete document index and score matrix remain on the document device, and the default scoring budget alone can be ~400 MB fp32 in addition to that index and model. Corpus size is a floor, not a hard upper bound (`01_dataset/02_sample.py:26-32`), so there is no bounded GPU-resident-index guarantee.

Minimal correction: return corpus embeddings on CPU with `convert_to_numpy=True`, score bounded document blocks on an explicitly chosen device and move each score block back to CPU; adapt the existing shared ranker to accept validation query IDs and reuse it in section 13. Keep the note that a single pair can exceed a scorer's element budget and that actual GPU feasibility must be measured. Do not call the installed scorer unchunked.

### C05 — Low: W&B preflight rejects valid authenticated setups

`11_bge_finetuning/02_train.py:10-11,21-23` requires `WANDB_API_KEY` in the environment unless offline. This rejects a user already authenticated through W&B's saved login, even though native `WandbCallback` initializes W&B (`transformers/integrations/integration_utils.py:738-767`) and can use that authentication. Conversely merely finding an environment variable does not prove authentication or that logging is active. It is not evidence that the existing explicit `wandb.finish()` sequencing is wrong: each loop constructs a new trainer, and the snapshot finishes after manual validation logging.

Minimal correction: permit documented secure pre-login or offline configuration, without printing credentials or prompting implicitly; allow W&B's native initialization to report real authentication/configuration errors. Verify four distinct BGE run names plus ColBERT and their validation logs later.

## Anticipated cross-review disagreements

- Simplicity may prefer leaving MNRL untouched and explaining false negatives. That is defensible pedagogically only if the explicit all-known-positive exclusion contract is relaxed and collision exposure is made visible; `NO_DUPLICATES` alone cannot establish that contract.
- A one-line all-pairs native scorer is genuinely simpler and its internal intermediate chunking is real. It does not bound resident GPU index memory; CPU storage plus a reused block scorer is the smallest correction that addresses that separate resource constraint.
- Ties can seem immaterial in teaching examples. Here three downstream consumers can interpret the very same saved run differently, so a shared deterministic tie policy is needed before asserting agreement between them.
- Tool-calling flexibility is useful pedagogically, but leaving tools enabled in a text-only rewrite adds a valid response shape the code does not handle. Removing tools for that one request keeps the demonstration simpler.
