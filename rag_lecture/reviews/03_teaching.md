## Findings and minimal corrections

### T01 — High — Missing opening vector geometry and numerical similarity comparison
`02_naive_encoder/01_load.py:4-10`, `03_similarity/01_rank.py:4-11`: the opening introduces token vectors and cosine formula, then immediately ranks real data. It has no concrete 2D points/arrows, dot-product vs cosine vs L2 worked comparison, or query-by-document similarity heatmap. The later `09_late_interaction/03_maxsim.py:15-24` heatmap is token-level MaxSim and `10_contrastive_learning/01_scores.py:21-28` uses an explicitly invented training-score matrix; neither teaches the initial single-vector geometry. **Fix:** one small, explicitly illustrative 2D example before real retrieval, showing two candidate vectors, dot/cosine/L2 and a labeled heatmap with an observation about magnitude versus direction; then retain the native real ranker. Avoid claiming a real embedding result.

### T02 — Medium — Pooling lesson demonstrates only two retrieval representations
`02_naive_encoder/02_encode.py:9-23`, `06_pooling/01_modules.py:4-10,16-27`, `06_pooling/02_compare.py:3-15`: there is a useful native mean module and normalize-norm display, and a same-weight CLS-vs-masked-mean retrieval comparison. Transformer pooler is explained as distinct but not actually inspected; max pooling is not shown; normalization is not compared by retrieval or vector-angle example. **Fix:** demonstrate pooler output and native max pooling on the existing small hidden-state batch, labeled clearly; compare a small number of coordinates/norms, and show that cosine rankings are invariant to nonzero-vector normalization. Add a full-corpus max run only if that is a required experiment; do not train extra models.

### T03 — High — Atlas does not deliver the requested measured like-for-like before/after
`04_embedding_atlas/01_explore.py:18-34` actually projects joint CLS vectors and computes original-space cosine neighbors; this is a genuine early Atlas. `07_dense_models/03_atlas.py:3-16` projects BGE, but the first sample is 16 questions + 100 documents and the second is 8 + 32; the instruction to repeat earlier representations is not an implemented comparison, and no neighbor overlap/relevance is measured. Also the pooled representation is not displayed in section 06 despite the prose implying section 06 explored it. **Fix:** use one shared list of actual question/document IDs for CLS and BGE (optionally mean), show side-by-side widgets plus a tiny native-neighbor table with matched question-to-document top-k IDs/overlap and labeled-positive hits. Make the sample limitation explicit; do not compare raw 2D coordinates from independently fitted PCAs or claim improvement beforehand.

### T04 — High — All metrics are computed, but not plotted
`05_retrieval_evaluation/01_metrics.py:18-20,36-45` configures accuracy, precision, recall, MRR, nDCG and MAP at all four cutoffs and displays the ledger. `05_retrieval_evaluation/02_plot.py:10-15` plots only accuracy and recall for the initial run. `20_comparison/01_results.py:12-13` is a table, while `20_comparison/02_agreement.py:22-25` plots run overlap, not relevance effectiveness. **Fix:** use the existing ledger to plot all six effectiveness metrics across cutoffs, preferably faceted and with a small selected set of runs to avoid unreadable spaghetti. Keep the TrecTools agreement plot separately labeled. Add an observation comparing, for example, first-hit and multi-positive recall without promising a result.

### T05 — High — Graph drawing is a flowchart, not an explanation of graph retrieval
`assets/graph-retrieval.svg:1` has three unlabeled circles and arrows, “Graph search,” and “Source papers”; it never shows a question, labeled entities/relations, seeds, traversal or provenance-to-evidence mapping. `18_graph_construction/01_extract.py:4-10`, `19_hipporag/01_index.py:4-18` do explain extraction and PageRank abstractly, but do not walk a student through what gets retrieved. The generated NetworkX plot (`18_graph_construction/02_graph.py:10-22`) draws node names and arrows but not relation labels on edges. **Fix:** replace or augment the shared diagram with an explicitly fictional, non-measured miniature: question “What connects compound A to condition C?” → paper P1 says “A interacts with B” and paper P2 says “B is associated with C” → labeled predicted edges A —interacts_with→ B —associated_with→ C with P1/P2 provenance → seed A, traverse/weight via B → retrieve P1 and P2 as evidence. State this is an illustration, not observed extraction, a medical claim, or a guarantee of the exact HippoRAG ranking; explain its OpenIE/index is separate from the GLiNER demo. Label relation edges in the actual small graph where practical. Ask students to trace a returned paper back to its supporting predicted edge and source text.

## Anticipated disagreements and boundaries

- **Simplicity vs pedagogy:** one native 2D comparison and one matched neighbor table add code, but address distinct missing concepts; do not build a reusable geometry framework or extra experiment runner.
- **Correctness vs visual clarity:** the toy graph needs labeled relation/provenance and question seeds, but should not pretend to reproduce HippoRAG's full internal scoring or an actual biomedical finding. A small hypothetical path plus actual source inspection is safer than a visually impressive invented benchmark.
- **Pooling breadth vs runtime:** small hidden-state max/pooler inspection is cheap to teach; a new full-corpus run is optional unless explicitly required. Keep pooling and normalization conceptually distinct.
- **Metrics vs clutter:** all six metrics matter, but faceting/selected models is clearer than every run on one plot. Keep evaluator as the sole effectiveness calculator and TrecTools as overlap only.
- **Licensing vs repetitive caveats:** flag non-commercial and dataset attribution once with primary cards; do not annotate every experiment with boilerplate or infer legal permissions from model names.
